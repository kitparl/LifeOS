# 08 Aug — Increment 1: Curated Resources + Knowledge Notes in Learning

Follow-up to [`08Aug.md`](08Aug.md). That document delivered the learning-track data model,
the seeder and the three views. This increment closes two gaps found while using it:

1. Most concepts had **no resources of their own** — only 55 resources existed across the
   whole track, and 44 of those were attached to phases, which the UI never displayed. Opening
   a concept usually showed "No resources linked."
2. There was **nowhere to write deep notes** against a concept. The `knowledge_notes` module
   already existed but was completely disconnected from learning.

Scope: no redesign, no new module. Extends the existing learning module and reuses
`knowledge_notes` as-is for storage.

---

## 1. Resource curation

### Principle: every resource has to earn its place

Rules applied while curating:

- **One canonical source per idea.** No "here are 5 tutorials on the same thing."
- **Prefer primary documentation** (OpenAI, Anthropic, LangGraph, MCP, pgvector, OpenTelemetry,
  Kubernetes, Postgres) over blog restatements, because docs stay accurate and are the thing
  you will actually read at work.
- **Videos only where a video genuinely teaches better** — intuition (3Blue1Brown), building
  from scratch (Karpathy), long-form project walk-throughs (freeCodeCamp), or Indian-context
  agentic walkthroughs (Krish Naik playlists).
- **Papers only where the paper is the clearest source** and short enough to read:
  ReAct, RRF, HNSW, LoRA, QLoRA, MemGPT, LLM-as-a-Judge.
- **No filler.** No "top 10 prompt tips", no course-selling landing pages, no aggregator
  listicles, no "awesome-*" link dumps.
- **Backend-engineer bias.** Where an LLM problem maps onto something you already know, the
  resource is the backend one: Stripe idempotency for tool re-execution, AWS Builders' Library
  for retries/backoff, Fowler for circuit breakers, Saga for compensation, Google SRE for SLOs.

### What changed

| | Before | After |
|---|---|---|
| Total resources | 55 | 220 |
| Concept-level | 11 | 172 |
| Phase-level | 44 | 48 |
| Concepts with ≥1 own resource | 8 of 80 | 80 of 80 |
| Distinct URLs | — | 129 |

Mix: 128 docs, 40 articles, 15 playlists, 11 videos, 9 repos, 7 papers, 6 courses, 4 books.
Priority split: 134 `primary`, 83 `supporting`, 3 `optional`.

Every resource carries `last_verified_at: 2026-08-08`. Re-verify quarterly; the seeder is
idempotent, so fixing a dead URL is a one-line JSON edit plus a re-seed.

### Depth guidance instead of a new column

The ask was "required depth", not just "more links". Rather than adding a schema column, the
depth statement lives in each concept's `summary`, which the seeder owns and refreshes. Each of
the 80 summaries now says how far to go and — importantly — where to stop. Examples:

- `attention-intuition` — "Depth: intuition for why cost grows with context length. Do NOT derive attention."
- `semantic-caching` — "Depth: know the correctness risk — a near-duplicate query is not the same query. Define a similarity threshold and an invalidation rule."
- `lora-qlora-peft` — "Depth: decision-level only. Know what LoRA changes and when it beats prompting plus retrieval."
- `tool-idempotency` — "Depth: agent steps get re-executed — every mutating tool needs an idempotency key. Reuse your payments model."

For the 20 project/deliverable concepts the summary states the artifact instead
("Deliverable: …"), so a project week can't quietly become a reading week.

`priority` and `duration_minutes` carry the rest of the depth signal: read the `primary` rows,
skim `supporting` only if the primary one didn't land.

### Bug fixed: invisible phase resources

Phase-level resources (channels, playlists, course hubs) were seeded but unreachable, because
`LearningItem` had no `resources` relationship and neither view rendered them. Now:

- `LearningItem.resources` is a read-only relationship restricted to rows where
  `concept_id IS NULL`, so concept rows aren't double-counted.
- `PhaseResponse.resources` exposes them, and the track detail view lists them under each phase.
- `ConceptResponse.inherited_resources` carries the parent phase's resources, and the concept
  detail view shows them in a separate **Phase resources** panel.

Phase 10 (flagship project) had zero phase resources and now has four. A test asserts that no
phase and no concept can ship without at least one resource.

## 2. Knowledge notes attached to concepts

### Requirement

From a concept, write a real note — into an **existing subject** you pick, or a **new subject**
you name on the spot — without leaving the learning flow, and have that note be a first-class
knowledge note (searchable, editable, indexed) rather than a second copy of the notes feature.

### Design

`knowledge_notes` stays untouched and remains the single store for notes. Learning owns a link
table, so the dependency points one way (learning → knowledge_notes).

```
learning_concepts ──< learning_concept_notes >── knowledge_sections
                                                        │
                                          knowledge_chapters ── knowledge_subjects
```

`learning_concept_notes`: `id`, `user_id`, `concept_id` (FK cascade), `section_id` (FK cascade),
`created_at`, unique on `(concept_id, section_id)`. New table, so `create_all` handles it — no
entry needed in `core/migrations.py`.

### Placement rule

A note written from a concept lands at:

- **Subject** — the one you chose, or a newly created one with the title you typed (icon `📚`).
- **Chapter** — the concept's **phase title**, reused if a chapter with that title already
  exists in the subject. So one subject naturally mirrors the track's phase structure instead
  of accumulating loose sections.
- **Section** — titled after the concept unless you override it.

Writing a second note for another concept in the same phase reuses the same chapter. The form
also pre-selects the subject already used for that concept, so notes stay together.

### API

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/v1/learning/concepts/{id}/notes` | Linked notes with subject/chapter context and a 200-char snippet |
| `POST` | `/api/v1/learning/concepts/{id}/notes` | Attach a note: `subject_id` (existing), `subject_title` (new), `chapter_id`, or `section_id` to link a note that already exists |
| `DELETE` | `/api/v1/learning/concepts/{id}/notes/{note_id}` | Unlink only — **the note itself is kept** |

`ConceptNoteCreate` rejects a body that names no target. Re-posting the same
`(concept_id, section_id)` returns the existing link instead of duplicating it.

Every read and write is scoped by `user_id`; a concept, subject, chapter or section belonging to
another user returns 404, never 403, so IDs aren't confirmed to an attacker.

### UI

One new panel on the existing concept detail page — no new route, no new component, same
Ubuntu-style `panel` / `title-bar` / `input-field` / `btn-primary` classes:

- **Knowledge notes** — linked notes (title, `subject · chapter`, snippet, `Unlink`), each
  linking through to `/knowledge/{subject_id}`, plus an inline form: subject dropdown whose
  first option is `＋ New subject…`, a new-subject name field shown only when that option is
  selected, note title (placeholder = concept title), and a note body.

The concept detail page also gained the **Phase resources** panel described above.

## 4. Applying the update

```bash
curl -X POST /api/v1/learning/tracks/seed \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"slug":"ai-systems-engineering"}'
```

Or press **Seed AI Systems** on `/learning/tracks`. Re-seeding adds the new resources and
refreshes summaries while preserving `confidence`, `can_explain`, `failure_modes_known`,
`tradeoffs_known`, `artifact_url`, `is_consumed`, resource `notes` and `completed_at`. Logged
sessions and attached notes are untouched.
